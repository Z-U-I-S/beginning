# 二、数据结构设计

## 2.1 棋盘：二维数组 + 方块对象

棋盘在内存里是一个 4×4 的二维数组 `board`，每格要么是 `null`（空格），要么是一个**方块对象**：

```js
let board = [];
// board[r][c] = null 或 { id, value, row, col, el }
```

| 字段 | 类型 | 含义 | 为什么需要它 |
| --- | --- | --- | --- |
| `id` | number | 方块自增编号 | 调试时区分“哪一块”，每块身份唯一 |
| `value` | number | 方块数字（2、4、8…） | 决定配色、字号和合并结果 |
| `row` / `col` | number | 方块在棋盘上的行、列 | 渲染时换算成 CSS 的 left / top |
| `el` | HTMLElement | 该方块对应的 `<div class="tile">` | 改样式、加动画、删除都靠它 |

**为什么不用“二维数字数组”直接当棋盘？** 因为动画需要一个稳定的“身份”。数字 2 在棋盘上可能同时存在好几块，如果只存数字，JS 无法知道“屏幕上那个 div”对应棋盘上的哪一个 2，也就没法只让它平移。给每一块一个对象和它专属的 DOM 元素后，“移动”就变成“改这一块的 row/col，让它自己滑过去”，动画天然成立。

## 2.2 渲染层的两条数据通道

| 通道 | 内容 | 用途 |
| --- | --- | --- |
| `board`（对象矩阵） | 带 `el` 的方块对象 | 渲染、动画、增删方块 |
| `currentValues()`（数字矩阵） | 纯数字 4×4 数组 | 交给核心算法算、交给 AI 决策、写进历史记录 |

两者通过 `currentValues()` 单向转换：

```js
function currentValues() {
  const values = [];
  for (let r = 0; r < SIZE; r++) {
    const row = [];
    for (let c = 0; c < SIZE; c++) row.push(board[r][c] ? board[r][c].value : 0);
    values.push(row);
  }
  return values;
}
```

## 2.3 历史记录的数据结构

每局结束会生成一条记录，追加进 `records` 数组并写入 localStorage：

```js
const record = {

  maxTile,        // 本局最大方块

```

# 三、核心算法：移动与合并

2048 的规则只有一句话：**所有方块朝同一个方向滑到底，数字相同的两块相撞就合并成两倍**。难点在于“同一块在一次移动中只能合并一次”，以及“四个方向要复用同一套逻辑”。

## 3.1 把四个方向统一成“线”

不管是上下左右，移动都发生在“一条线”上（一行或一列），而且**线的读取顺序必须与移动方向一致**：从最靠近目标边界的那一格开始读。

```js
function lineCoords(dir, i) {
  const coords = [];
  for (let j = 0; j < SIZE; j++) {
    if (dir === 'left')  coords.push([i, j]);            // 行 i：从左到右
    if (dir === 'right') coords.push([i, SIZE - 1 - j]); // 行 i：从右到左
    if (dir === 'up')    coords.push([j, i]);            // 列 i：从上到下
    if (dir === 'down')  coords.push([SIZE - 1 - j, i]); // 列 i：从下到上
  }
  return coords;
}
```

这样一来，**四个方向都变成了“向左”**：把线上的 4 个数字按 `coords` 的顺序取出来，用同一个 `planLine()` 处理，再按同样的顺序写回去即可。代码量从“四套逻辑”降到“一套逻辑 + 一张坐标表”。

以 `left` 为例，`i = 0` 时返回 `[[0,0],[0,1],[0,2],[0,3]]`，恰好就是第 0 行从左到右。

## 3.2 planLine：一次移动的全部规划

这是整个游戏的心脏：输入一行 4 个数字，输出“移动后的这一行 + 本次得分 + 一串按执行顺序排好的动作”。

```js
function planLine(cells) {
  const ops = [];      // 动作表，顺序执行即可完成整条线的移动
  const result = [];
  let gained = 0;

  // 1) 去掉空格，只留下有数字的方块，并记住它们原来的下标
  const blocks = [];
  for (let i = 0; i < cells.length; i++) {
    if (cells[i] > 0) blocks.push({ value: cells[i], index: i });
  }

  // 2) 从左往右扫：相邻两个数字相同就合并，否则单独滑过去
  let k = 0;
  let outIndex = 0;
  while (k < blocks.length) {
    const cur = blocks[k];
    const next = blocks[k + 1];
    if (next && next.value === cur.value) {
      const value = cur.value * 2;
      ops.push({ kind: 'merge', from: [cur.index, next.index], to: outIndex, value });
      result.push(value);
      gained += value;          // 合并得分 = 新方块的数值
      k += 2;                   // 两个块都被消耗掉
    } else {
      ops.push({ kind: 'slide', from: cur.index, to: outIndex });
      result.push(cur.value);
      k += 1;
    }
    outIndex++;
  }
  while (result.length < SIZE) result.push(0);

  const moved = ops.some((op) => op.kind === 'merge' || op.from !== op.to);
  return { result, gained, ops, moved };
}
```

分三步理解：

1. **先挤掉空格**。`blocks` 只保留有数字的格子，并记录它们原来的下标。这样“滑动”就自动完成了——第 k 个非空块最终一定落在第 k 个（或更靠前，如果前面发生了合并）位置。
2. **相邻贪心合并**。因为已经挤掉了空格，只需比较 `blocks[k]` 和 `blocks[k+1]`：相等就合并（`k += 2`，跳过两块），不等就单独滑过去（`k += 1`）。**这个 `k += 2` 就是“同一块一步只合并一次”的实现**——合并掉的两个块直接被跳过，绝不会被后面的块再次合并。
3. **按顺序记录动作**。`ops` 里的动作按“目标格子下标从小到大”排列，渲染层照着顺序搬方块就行。**这个顺序不是随便定的，而是动画与数据保持一致的关键**，原因见 3.5。

验证用例（`_tools/test-core.js` 会自动跑）：

| 输入行 | 输出行 | 得分 | 说明 |
| --- | --- | --- | --- |
| `[2,2,4,0]` | `[4,4,0,0]` | 4 | 两个 2 合并，4 滑到第二位 |
| `[2,2,2,2]` | `[4,4,0,0]` | 8 | 不连锁：第 1、2 个合并，第 3、4 个合并 |
| `[4,4,8,8]` | `[8,16,0,0]` | 24 | 8 + 16 = 24 |
| `[2,0,2,4]` | `[4,4,0,0]` | 4 | 中间的空格不影响相邻判断 |
| `[2,4,8,16]`（右移） | 原样 | 0 | `moved = false`，这一步不算有效移动 |

## 3.3 coreMoveBoard：把 4 条线拼回一张棋盘

```js
function coreMoveBoard(values, dir) {
  const board = values.map((row) => row.slice());   // 复制一份，不改原数据
  const ops = [];
  let gained = 0;
  let moved = false;

  for (let i = 0; i < SIZE; i++) {
    const coords = lineCoords(dir, i);
    const cells = coords.map(([r, c]) => board[r][c]);
    const plan = planLine(cells);

    if (plan.moved) moved = true;
    gained += plan.gained;

    for (const op of plan.ops) {
      if (op.kind === 'merge') {
        ops.push({
          kind: 'merge',
          from: [coords[op.from[0]], coords[op.from[1]]],
          to: coords[op.to],
          value: op.value,
        });
      } else {
        ops.push({ kind: 'slide', from: coords[op.from], to: coords[op.to] });
      }
    }
    coords.forEach(([r, c], k) => { board[r][c] = plan.result[k]; });
  }
  return { board, gained, moved, ops };
}
```

它有 4 个返回值，正好服务两类调用者：

| 返回值 | 内容 | 谁在用 |
| --- | --- | --- |
| `board` | 移动后的数字棋盘 | AI 模拟走子、判断是否结束 |
| `gained` | 本次得分 | 累加到当前分数 |
| `moved` | 是否真的发生了移动 | 决定“这一步算不算数” |
| `ops` | 动作表（棋盘坐标，已按安全顺序排列） | 渲染层按顺序搬运方块、播放动画 |

**这一点是本项目复用性最好的设计**：规则只写一遍，界面、AI、测试三方共用。任何一方改了规则，另外两方立刻同步。

## 3.4 胜负判定

```js
function coreHasMoves(values) {
  for (let r = 0; r < SIZE; r++) {
    for (let c = 0; c < SIZE; c++) {
      if (values[r][c] === 0) return true;                                   // 有空格
      if (c + 1 < SIZE && values[r][c] === values[r][c + 1]) return true;    // 右邻相同
      if (r + 1 < SIZE && values[r][c] === values[r + 1][c]) return true;    // 下邻相同
    }
  }
  return false;   // 既没有空格，也没有可合并的相邻块 → 本局结束
}
```

只需检查“右邻”和“下邻”，因为每一对相邻格子会被左右或上下关系各覆盖一次，不必重复判断。

# 四、渲染与动画

## 4.1 用 left / top 而不是 transform

方块是绝对定位的 `<div>`，位置由 CSS 的 `left` / `top` 决定，并对这两个属性加了过渡：

```css
.tile {
  position: absolute; left: 0; top: 0;
  width: calc(25% - var(--gap) * 0.75);
  height: calc(25% - var(--gap) * 0.75);
  transition: left var(--slide) ease-in-out, top var(--slide) ease-in-out;
}
```

位置换算公式（`--gap` 是方块间距，`--pad` 是棋盘内边距）：

- 一格宽度 = `(棋盘内容宽 - 3 × gap) / 4`，写成百分比就是 `25% - gap × 0.75`
- 第 n 格的左偏移 = `n × (一格宽 + gap)`，也就是 `n × (25% + gap × 0.25)`

于是 JS 里只改一个数字就能让方块滑动：

```js
function placeTile(tile) {
  const step = 'calc(25% + var(--gap) * 0.25)';
  tile.el.style.left = `calc(${tile.col} * ${step})`;
  tile.el.style.top  = `calc(${tile.row} * ${step})`;
}
```

**为什么不用 `transform: translate`？** 因为 `translate` 里的百分比是相对元素自身尺寸的，还要额外拼出间隙的像素值，表达式更绕；而 `left`/`top` 的百分比直接相对容器，用 `calc()` 一次就能写清楚，`transition` 对 `calc(百分比 + 像素)` 的插值在各浏览器上也最稳定。棋盘只有 16 个方块，性能完全不是问题。

## 4.2 动画时序：让“滑动 → 合并”看起来连续

CSS 里定义了两个关键帧：

```css
@keyframes tile-appear { from { opacity: 0; transform: scale(.3); } to { opacity: 1; transform: scale(1); } }
@keyframes tile-merge  {
  0%   { opacity: 0; transform: scale(.3); }
  60%  { opacity: 1; transform: scale(1.16); }
  100% { opacity: 1; transform: scale(1); }
}
.tile--new    { animation: tile-appear 160ms ease-out var(--slide) both; }
.tile--merged { animation: tile-merge  200ms ease-out var(--slide) both; }
```

注意动画最后那个 `var(--slide)`——它是 **animation-delay**。也就是：

```text
0ms ─────────── 120ms ─────────── 320ms
│  旧方块滑动    │  新方块弹出放大   │
│  (left/top)   │  (scale + fade)  │
```

- 合并产生的“新方块”**立刻**被创建并放在目标格，但用 `animation-delay: 120ms` + `animation-fill-mode: both` 让它先隐藏（`both` 会把 0% 关键帧的 `opacity:0` 提前应用），等旧方块滑到位后再弹出，观感上就是“两块撞在一起 → 蹦出新数字”。
- `transition` 时长与 `animation-delay` 都用同一个 CSS 变量 `--slide`，JS 里的 `SLIDE_MS = 120` 与它保持一致，避免出现“动画还没播完就删元素”的闪烁。

## 4.3 旧方块的清理

合并后原来的两个方块必须从 DOM 里删掉，但**不能马上删**，否则会看到方块凭空消失：

```js
if (toRemove.length) {
  setTimeout(() => { for (const node of toRemove) node.remove(); }, SLIDE_MS);
}
```

`setTimeout(..., SLIDE_MS)` 让它们先滑完 120ms，再统一移除。

## 4.4 配色系统：渐变底色 + 分段色阶

配色表是一张“数字 → 样式”的映射，方便按题目要求调整：

```js

  4:    { from: '#FBDCD4', to: '#F9CFC5', text: '#FFFFFF', shadow: 'strong' },
  8:    { from: '#F7C1B4', to: '#F5B3A4', text: '#FFFFFF', shadow: 'strong' },
  16:   { from: '#F2A38E', to: '#F0937B', text: '#FFFFFF', shadow: true },
  32:   { from: '#ED7F68', to: '#EA6E55', text: '#FFFFFF', shadow: true },
  64:   { from: '#F0634C', to: '#E8452F', text: '#FFFFFF', shadow: false }, // 红色
  128:  { from: '#FCF6AF', to: '#FAF08C', text: '#FFFFFF', shadow: true }, // 浅黄
  256:  { from: '#F8E87A', to: '#F6E14F', text: '#FFFFFF', shadow: true },
  512:  { from: '#F4DC55', to: '#F0CF14', text: '#FFFFFF', shadow: true },
  1024: { from: '#E8C33C', to: '#E0B400', text: '#FFFFFF', shadow: false },
  2048: { from: '#D6A61C', to: '#C08A00', text: '#FFFFFF', shadow: false }, // 深黄
};
const TILE_STYLE_HIGH = { from: '#2b2b2b', to: '#0a0a0a', text: '#FFFFFF', shadow: false }; // 4096+
```

色阶满足题目要求：

| 数字区间 | 底色 | 数字颜色 |
| --- | --- | --- |
| 2 | 纯白 `#FFFFFF` | 深灰 `#5f5b56`（白底白字会看不见，见第九章） |
| 4 → 64 | 浅粉 → 深红，逐级加深 | 白色 |
| 64 | 红色 `#E8452F` | 白色 |
| 128 → 2048 | 浅黄 `#FAF08C` → 深黄 `#C08A00` | 白色 |
| 4096 及以上 | 黑色 `#0a0a0a` | 白色 |

**「由浅至深」不能只靠眼睛，要用数字卡住。** 4~16 的底色如果太浅，白字就几乎读不出来，所以项目里把浅色档整体压深了一轮，并在浏览器测试里用亮度公式 `0.299R + 0.587G + 0.114B` 给每一档设了上限：

| 数字 | 亮度上限（越小越深） | 本轮实测 |
| --- | --- | --- |
| 4 | < 235 | 228 |
| 8 | < 215 | 208 |
| 16 | < 190 | 184 |

同时测试还会检查 2→64、128→2048 两段色阶的亮度必须**逐级下降**，避免调色时不小心把顺序弄反。

每个方块用 `linear-gradient(135deg, from, to)` 生成**渐变底色**，即使相邻两个数字色阶接近，也能靠渐变方向看出立体感：

```js
node.style.background = `linear-gradient(135deg, ${style.from}, ${style.to})`;
node.style.color = style.text;
node.className = 'tile' + (style.shadow ? ' tile--shadow' : '');
```

`shadow` 标记用来给浅色底（4 / 8 / 16 / 32 / 128 / 256 / 512）上的白字加投影：

```css
.tile--shadow { text-shadow: 0 1px 3px rgba(0, 0, 0, .45), 0 0 1px rgba(0, 0, 0, .35); }
```

## 4.5 字号自适应

方块里的数字位数不同，用一个 `data-len` 属性记录位数，CSS 按位数选字号：

```js
node.dataset.len = String(String(value).length);
```

```css
.tile[data-len="1"], .tile[data-len="2"] { font-size: clamp(18px, 7.4vw, 32px); }
.tile[data-len="3"] { font-size: clamp(16px, 6.2vw, 27px); }
.tile[data-len="4"] { font-size: clamp(13px, 5vw, 22px); }
.tile[data-len="5"], .tile[data-len="6"] { font-size: clamp(11px, 4vw, 17px); }
```

`clamp(最小值, 期望值, 最大值)` 让字号既能随窗口缩放，又不会大到溢出方块。

## 4.6 图层：胜利浮层为什么会被方块盖住

游戏里有一句看似无害的代码：

```js
node.style.zIndex = String(++zIndex);   // 新方块永远盖住旧方块
```

让刚出现的方块在最上层是合理的，但 `zIndex` 是全局自增的：一局两千步下来它会涨到几千。而“本局结束 / 达成 2048”的浮层原本写的是 `z-index: 50`——于是**玩到中后期，方块就会盖在胜利浮层上面**，看起来就是提示框被数字块戳穿。

修法不是把浮层的数字改大（那只是把问题往后推，方块迟早还会超过），而是**让方块们自己关起门来比大小**：

```css
/* 方块层：z-index 只写 1，让它成为独立的“层叠上下文” */
.tile-layer { position: absolute; inset: var(--pad); z-index: 1; }

/* 浮层只要比方块层大就行，方块内部的数字再大也只在方块层里生效 */
.board-overlay { position: absolute; inset: 0; z-index: 5; }
```

这里的关键概念是**层叠上下文（stacking context）**：一个元素只要满足“定位 + z-index 不为 auto”等条件，就会创建自己的层叠上下文，它所有后代的 `z-index` 都只在**这个上下文内部**比较，不可能越级去盖外面的兄弟元素。所以方块层内部的 783 永远小于浮层的 5。

> 这条规则还顺带解释了一个常见困惑：**为什么把子元素的 `z-index` 调到 99999 也盖不住某个元素？** 因为它和那个元素根本不在同一个层叠上下文里。

浏览器测试里专门加了一条断言来盯住这个问题：连续创建 400 个方块把 `z-index` 抬到几百，然后显示浮层，再用 `document.elementFromPoint()` 取棋盘正中央最上层的元素，**必须命中浮层而不是方块**。

# 五、游戏流程与状态机

## 5.1 关键状态变量

| 变量 | 含义 |
| --- | --- |
| `score` / `best` | 本局分数 / 历史最高分 |
| `moves` | 本局有效步数 |
| `won` | 本局是否已合出 2048（只用于触发一次胜利浮层） |
| `roundEnded` | 本局是否已结束（结束后成绩已写入历史） |
| `roundStartAt` / `roundFrozenMs` | 本局开始时间 / 结束时的用时（用于“本局时长”） |
| `undoStack` | 撤回栈，每走一步压入一个快照 |
| `lastSavedRecordId` | 最近写入历史的那条记录 id，供死局撤回时撤销 |

## 5.2 doMove：走一步的五个阶段

人类按键、触屏滑动、AI 决策最终都调用同一个 `doMove(dir)`：

```js
function doMove(dir) {
  if (roundEnded) return false;
  flushRemovals();                             // 清掉上一批待删除的旧方块

  const plan = coreMoveBoard(currentValues(), dir);
  if (!plan.moved) return false;               // 该方向走不动，直接忽略

  // 1) 记录快照，供撤回使用
  undoStack.push({ values: currentValues(), score, moves });

  // 2) 按 ops 的顺序搬运方块（顺序是算法保证过的，见 3.4）
  //    普通滑动直接 placeTile；合并则是两个旧方块滑到同一格，
  //    动画结束后再删掉它们，并在该格生成一个两倍数值的新方块
  for (const op of plan.ops) { /* … */ }

  // 3) 结算分数 + 新方块
  score += plan.gained;
  moves += 1;
  if (score > best) { best = score; saveBest(); }
  addRandomTile('new');
  pulseScore();
  renderStats();

  checkRoundState();
  return true;
}
```

顺序不能乱：

1. **先判断能不能走**——如果这个方向走不动（比如所有方块都已经贴边），这一步不消耗步数、不生成新方块、不压入撤回栈。
2. **再压快照**——快照必须在改动之前取，且只取“有效移动”，否则撤回会出现“点了没反应”的假撤回。
3. **动画与数据同步**——先改 `board` 对象矩阵和 row/col，再调 `placeTile` 触发过渡。
4. **结算与渲染**——加分、加步数、更新最高分、生成新方块、刷新顶部数字。
5. **最后判断状态**——是否达成 2048、是否无路可走。

## 5.3 多次撤回的实现

撤回的本质是“快照 + 整体还原”，实现非常简单：

```js
undoStack.push({ values: currentValues(), score, moves });   // 备份
```

```js
function undo() {
  if (undoStack.length === 0) return;
  // …（死局撤回的额外处理，见 5.4）
  const snap = undoStack.pop();
  score = snap.score;
  moves = snap.moves;
  rebuildBoard(snap.values);      // 清空并重建所有方块 DOM
  won = coreMaxTile(snap.values) >= 2048;
  renderStats();
}
```

- **为什么可以多次撤回**：栈里保存的是每一步之前的完整局面，弹一次退一步，弹 N 次退 N 步；按钮上的数字就是 `undoStack.length`。
- **为什么撤回时不用动画**：`rebuildBoard()` 直接清空 `tileLayer` 再重建，新元素没有“上一个位置”，自然不会播放滑动。撤回追求的是“立刻回到那一刻”，瞬移反而更符合直觉。
- **防爆栈**：`if (undoStack.length > 500) undoStack.shift();` 限制最多存 500 步，正常一局到不了这个量。

## 5.4 死局也能撤回（并把战绩一起撤销）

本局结束时记录已经写进历史了。如果玩家此时点“撤回”，需要把这条记录也去掉，否则会出现“同一个局面留下两条战绩”：

```js
if (roundEnded) {
  if (lastSavedRecordId) {
    records = records.filter((r) => r.id !== lastSavedRecordId);  // 撤销刚写入的记录
    lastSavedRecordId = null;
    persistRecords();
    highlightRecordId = null;
    renderHistory();
  }
  roundEnded = false;
  hideOverlay();
}
```

本局结束浮层上的「撤回一步」按钮正是调用了 `undo()`，所以玩家在死局界面可以一键回到上一步继续玩。

## 5.5 结束本局与写入记录

```js
function endRound(reason) {
  if (roundEnded) return;               // 幂等：同一局只写一次
  roundEnded = true;
  roundFrozenMs = Date.now() - roundStartAt;   // 冻结本局时长

  const values = currentValues();
  const maxTile = coreMaxTile(values);
  const record = { /* 见 2.3 */ };
  records.push(record);
  if (records.length > 200) records = records.slice(-200);  // 只留最近 200 局
  lastSavedRecordId = record.id;
  highlightRecordId = record.id;
  persistRecords();
  // …
}
```

三种结束原因：

| `reason` | 触发时机 |
| --- | --- |
| `'gameover'` | 棋盘填满且无法再合并 |
| `'win'` | 达成 2048 后点“保存并开新局” |
| `'abandon'` | 一局还没结束就点了“新游戏” |

`if (roundEnded) return;` 这一行是幂等保护：无论结束流程被触发几次，一局只会留下一条记录。

## 5.6 计时器

“本局时长”要一直走动，但结束后必须停住：

```js
function elapsedMs() {
  if (roundEnded) return roundFrozenMs;   // 结束后固定
  return Date.now() - roundStartAt;       // 进行中实时计算
}
function startTimer() {
  setInterval(() => { el.statTimer.textContent = formatDuration(elapsedMs()); }, 250);
}
```

每 250ms 刷新一次显示即可（人的眼睛分辨不出更细的差别），用 `Date.now()` 差值算时间比累加计数器更准——即使浏览器把 `setInterval` 节流，时间也不会走偏。

## 6.1 localStorage 的三个键

| 键名 | 内容 | 读取时机 |
| --- | --- | --- |
| `game2048.best` | 历史最高分 | 页面初始化 |
| `game2048.records` | 全部战绩数组（JSON） | 页面初始化 |
| `game2048.theme` | `'light'` / `'dark'` | 页面初始化 |

读写都包了 `try / catch`：

```js
function readStore(key, fallback) {
  try {
    const raw = localStorage.getItem(key);
    return raw === null ? fallback : JSON.parse(raw);
  } catch (err) {
    return fallback;   // 浏览器禁用了本地存储也不影响游戏
  }
}
function writeStore(key, value) {
  try { localStorage.setItem(key, JSON.stringify(value)); } catch (err) { /* 忽略 */ }
}
```

这几行同时满足了两条验收标准：**「新一局不清零」**（最高分与局数存在本地，开始新一局不会丢）和**「刷新后保留所选主题」**。

## 6.2 侧边栏渲染

```js
function renderHistory() {

  el.historyList.innerHTML = '';
  el.historyEmpty.hidden = records.length > 0;
```

- 每局结束都会调用 `renderHistory()`，并给最新一条加上 `.is-new` 类，产生高亮底色 + 从右侧滑入的动画，玩家一眼就能在侧边栏看到“我这局进了历史记录”。

# 七、AI 自动演示（任务书阶段二）

阶段二的硬指标是：**AI 全程无需人工操作，自动合出 1024 方块（合出 2048 为加分项）**。这里采用 2048 领域公认效果最好的 **Expectimax（期望最大）搜索**。

## 7.1 为什么是 Expectimax，而不是普通的最小最大搜索

普通棋类可以假设“对手总是走最坏的一步”，用 Minimax。但 2048 里没有对手，**只有随机**：新方块出现在哪个空格、是 2 还是 4，都是概率事件，而且概率已知（2 占 90%、4 占 10%，空格均匀随机）。

所以搜索树里有两类节点：

| 节点类型 | 谁在决策 | 取值方式 |
| --- | --- | --- |
| 玩家节点（Max） | AI 选方向 | 四个方向里取**最大** |
| 随机节点（Chance） | 系统随机放方块 | 按概率求**加权平均（期望）** |

两层交替展开，得到的期望值就代表“从这个局面出发，平均能拿到多好的结果”。

## 7.2 指数化棋盘：让计算快一倍

搜索过程中要反复合并、比较，用“指数”代替“数字”更快也更省内存：`0` 表示空，`1` 表示 2，`2` 表示 4，……，`11` 表示 2048。

```js
function toExps(values) {
  const out = new Array(SIZE * SIZE);
  for (let r = 0; r < SIZE; r++) {
    for (let c = 0; c < SIZE; c++) {
      const v = values[r][c];
      out[r * SIZE + c] = v > 0 ? Math.round(Math.log2(v)) : 0;
    }
  }
  return out;
}
```

好处：两个数字能不能合并，只要判断**指数是否相等**；合并结果就是**指数 +1**。位运算 `1 << e` 也能直接还原出分数。

## 7.3 fastMove：AI 专用的高速移动

核心规则与 `coreMoveBoard` 完全一致，但为搜索做了两点优化：一次只处理一行、用预计算的下标表避免反复算坐标。

```js
const LINE_INDEX = (() => {
  const table = {};
  for (const dir of DIRECTIONS) {
    const lines = [];
    for (let i = 0; i < SIZE; i++) {
      lines.push(lineCoords(dir, i).map(([r, c]) => r * SIZE + c));
    }
    table[dir] = lines;
  }
  return table;
})();

function fastMove(exps, dir) {
  const out = new Array(SIZE * SIZE);
  let gained = 0, moved = false;
  for (const line of LINE_INDEX[dir]) {
    const vals = [];
    for (let k = 0; k < SIZE; k++) if (exps[line[k]]) vals.push(exps[line[k]]);
    let p = 0, oi = 0;
    while (p < vals.length) {
      if (p + 1 < vals.length && vals[p] === vals[p + 1]) {
        const e = vals[p] + 1;      // 指数 +1 = 数字翻倍
        out[line[oi]] = e;
        gained += 1 << e;
        p += 2;
      } else { out[line[oi]] = vals[p]; p += 1; }
      oi++;
    }
    while (oi < SIZE) { out[line[oi]] = 0; oi++; }
    for (let k = 0; k < SIZE; k++) if (out[line[k]] !== exps[line[k]]) moved = true;
  }
  return { board: out, gained, moved };
}
```

> 测试里专门做了一致性校验：**3000 个随机棋盘 × 4 个方向**，`fastMove` 与 `coreMoveBoard` 的结果必须完全相同（见第八章）。这是防止“两套规则”产生分叉的关键保险。

## 7.4 评估函数：怎么判断一个局面好不好

搜索到指定深度后，用一个打分函数给局面估值。最终采用的方案是把五个经验性因素加权求和：

```js
const WEIGHTS = { empty: 2.7, mono: 1.0, smooth: 0.1, corner: 1.2, merges: 0.6 };

function evaluateExps(exps) {
  // ① empty ：空格数量
  // ② mono  ：单调性——每行每列越朝向同一个方向递增/递减越好
  // ③ smooth：平滑度——相邻数字差越小越好
  // ④ corner：最大的数字待在四个角上，额外加分
  // ⑤ merges：相邻相同数字的对数，有得可合未来才有分
  return WEIGHTS.empty * empty
       + WEIGHTS.mono * mono
       + WEIGHTS.smooth * smooth
       + WEIGHTS.corner * maxExp * maxInCorner
       + WEIGHTS.merges * merges;
}
```

| 因素 | 直觉解释 | 权重 |
| --- | --- | --- |
| `empty`（空格数） | 空格是“活路”，空格越多越不容易被憋死 | 2.7 |
| `mono`（单调性） | 数字沿一个方向排成阶梯（如 128-64-32-16），合并链才顺畅 | 1.0 |
| `smooth`（平滑度） | 相邻数字差距小，才容易逐级合并 | 0.1 |
| `corner`（大数在角） | 最大的块缩在角落，不会被小方块推来推去 | 1.2 |
| `merges`（可合并对数） | 马上就能合的越多，短期收益越高 | 0.6 |

单调性的算法是“用较小的那个方向的累计落差作为惩罚”：

```js
for (let c = 0; c < SIZE - 1; c++) {
  const a = exps[r * SIZE + c];
  const b = exps[r * SIZE + c + 1];
  if (a > b) dec += a - b; else inc += b - a;
}
mono -= Math.min(inc, dec);
```

一行如果既大幅递增又大幅递减，说明它是“山峰形”，两个方向的落差都大，`min` 就大，惩罚也大；而整齐的阶梯形总有一个方向落差为 0，`min = 0`，不扣分。行与列都算一遍再累加。

> **为什么不换成更“高级”的评估函数？** 我们真的试过。另一种在公开的 2048 AI 里很常见的做法是把棋盘拆成“一行 4 格”，预先算出 65536 种行组合的分数表（空格、相邻同数、单调性、行内数字总和四项），评估时只查 8 次表，速度是加权版的 2~3 倍。理论上更快就能搜得更深、应该更强。但实测结果恰恰相反（见第八章）：**在同样的搜索深度下，查表版只能合出 128~256，而被“嫌弃”的加权版 8 局全部合出 2048**。原因是查表版完全没有“大数字要待在角落”的概念，浅层搜索时会被同分局面牵着走、反复横跳；加权版虽然朴素，却把“保住角落”这条最关键的策略直接写进了分数里。
>
> 这次对比留下了一个很实在的经验：**评估函数好不好，不能看它像不像教科书，要看它在同样的搜索深度下赢不赢**。所以项目里保留了这次实验的结论，最终采用简单可靠的加权版。

## 7.5 概率剪枝：让搜索不爆炸

一个随机节点最多有 16 个空格 × 2 种数字 = 32 个子节点，再往下展开会指数爆炸。解决方法是**概率剪枝**：累计概率太小的分支不再展开，直接用估值折算。

```js
const AI_PROB_CUTOFF = 0.0001;   // 累计概率低于 0.01% 就停止下探

let total = 0;
for (const idx of cells) {
  for (const pair of [[1, 0.9], [2, 0.1]]) {
    const condProb = pair[1] / cells.length;   // 条件概率：所有子节点之和恰好为 1
    const branchProb = prob * condProb;        // 累计概率：只用来决定要不要继续下探
    const next = exps.slice();
    next[idx] = pair[0];
    total += branchProb < AI_PROB_CUTOFF
      ? condProb * evaluateExps(next)                     // 剪枝：用估值代替继续搜索
      : condProb * expectimax(next, depth, true, branchProb); // 继续往下搜
  }
}
return total;
```

这里有**两个概率**，必须分清楚，写错了整局 AI 都会变傻：

| 概率 | 含义 | 用在哪 |
| --- | --- | --- |
| `condProb` = 0.9/n 或 0.1/n | 条件概率，同一个随机节点的所有子节点加起来正好是 1 | **乘在返回值上**，用来求期望 |
| `branchProb` = 上一层累计 × condProb | 走到这条分支的累计概率 | 只用于和阈值比较，**绝对不能拿来缩放返回值** |

> **我们在这上面栽过一次大跟头。** 最初的写法是“用累计概率加权求和，总和天然等于期望值”，听起来很有道理，实际上每个随机层都会再乘一次累计概率，等于把期望值连乘了好几遍：深度越深返回值越小，AI 于是被严重带偏——连“把 2048 留在角落”这种明显正确的一步都选不出来。当时所有的调参实验（换评估函数、加蛇形权重）全部得到“越调越差”的结论，直到把搜索数学改正过来才峰回路转：同一份评估函数，**修好前只能合出 128，修好后 8 局全部合出 2048**。
>
> 教训：**当所有参数调整都让结果变差时，先怀疑公式，而不是继续调参数。**

## 7.6 迭代加深 + 时间预算

搜索越深越准，但太深会卡住界面。这里用“**迭代加深**”：从 1 层开始一层层加深，时间用完就用上一层的结果。

```js
function aiChooseMove(values, options) {
  const maxDepth = options.maxDepth || 5;
  const timeBudget = options.timeBudget || 0;
  aiDeadline = timeBudget > 0 ? now() + timeBudget : Infinity;

  let exps = toExps(values);
  let bestMove = null;
  for (let depth = 1; depth <= maxDepth; depth++) {
    const results = [];
    for (const dir of DIRECTIONS) {
      const res = fastMove(exps, dir);
      if (!res.moved) continue;
      results.push({ dir, score: expectimax(res.board, depth - 1, false, 1) });
    }
    if (results.length === 0) break;
    if (aiOutOfTime() && depth > 1) break;      // 这一层没算完，丢弃
    results.sort((a, b) => b.score - a.score);
    bestMove = results[0].dir;
    if (aiOutOfTime()) break;
  }
  return { dir: bestMove, depth: reachedDepth, nodes: aiNodes, candidates: ... };
}
```

配合两层保护，AI 永远不会让页面卡死：

1. **时间闸门**：每搜索 1024 个节点检查一次 `now() > aiDeadline`，超时就返回当前估值。
2. **不完整层丢弃**：如果某一层没算完就被超时打断，这一层的结果不可靠，直接丢弃，沿用上一层。

界面上的“慢 / 中 / 快”三档就是给 `timeBudget` 和每步间隔各配一组参数：

```js
/* AI 每两步之间至少隔多久（毫秒）。搜索本身是同步计算，会短暂占用主线程，
   间隔太短会让页面连续卡顿，所以这里设一个 0.3 秒的保底间隔。 */
const AI_MIN_INTERVAL = 300;

/* 三档速度：delay 是两步之间的间隔（毫秒），budget 是每步的“思考时间上限”。
   实际间隔会取 delay 与 AI_MIN_INTERVAL 中较大的那个。 */
const AI_SPEED = {
  slow:   { delay: 900, budget: 250 },
  normal: { delay: 400, budget: 120 },
  fast:   { delay: 300, budget: 60 },
};
```

## 7.7 与游戏主循环对接

AI 的每一步都复用玩家走子的同一个函数，因此 AI 走的每一步同样会压入撤回栈、同样会被记入历史：

```js
function aiStep() {
  if (!aiRunning || roundEnded) { stopAI('已停止'); return; }
  const speed = AI_SPEED[el.aiSpeed.value] || AI_SPEED.normal;

  const result = aiChooseMove(currentValues(), { timeBudget: speed.budget, maxDepth: 5 });
  aiStats.depth = result.depth;
  aiStats.nodes = result.nodes;

  if (!result.dir) { stopAI('无路可走'); return; }
  const moved = doMove(result.dir);
  updateAiMeta();
  if (!moved || roundEnded) { stopAI(roundEnded ? '本局结束' : '已停止'); return; }
  // 间隔取“档位设定”和“保底 0.3 秒”里较大的那个
  aiTimer = setTimeout(aiStep, Math.max(AI_MIN_INTERVAL, speed.delay));
}
```

> **为什么要专门加一个 0.3 秒的保底间隔？** AI 的搜索是**同步**的：`aiChooseMove()` 一调用，主线程就被占住几十到几百毫秒，这期间浏览器既不能重绘也不能响应点击。如果两步之间只隔十几毫秒，就等于「卡 70ms → 歇 15ms → 又卡 70ms」，连续几百步下来页面几乎没有喘息时间，看起来就是一直在掉帧。把间隔抬到 0.3 秒之后，每一步都有明确的空闲窗口让浏览器完成重绘和动画，观感立刻顺了。
>
> 这也解释了“速度”三档的真实含义：它主要控制**每步愿意想多久**（决定棋力），而**间隔**有 0.3 秒下限兜底，不再允许把间隔调到很小。

- AI 演示期间键盘输入被忽略，避免人机互相打断；点按钮或在结束时自动停止。
- 状态条实时显示**搜索深度、评估节点数、当前最大方块**，把 AI 的“思考过程”可视化。
- 达成 2048 时 `checkRoundState()` 会触发胜利浮层并停止 AI。

# 九、几处需要说明的设计取舍

## 9.1 数字 2 的字体颜色

题目要求“**数字统一为白色**”且“**数字 2 底色为白色**”。这两条如果同时严格执行，白色的 2 会完全看不见。因此本项目按“**能看清**”这一底层目标处理：

- 方块 2：底色白色，数字用深灰 `#5f5b56`；
- 其余所有方块：数字统一白色；其中底色较浅的（4 / 8 / 16 / 32 / 128 / 256 / 512）额外加一层文字投影，保证白字在浅色渐变底上依然清晰。

如果一定要“全白”，只需把 `TILE_STYLE[2].text` 改回 `'#FFFFFF'` 即可，其余逻辑不受影响。

## 9.2 AI 演示期间屏蔽人工输入

若允许边按键盘边跑 AI，会出现“人按一下、AI 又走一步”的混乱，且撤回栈顺序会难以解释。因此 AI 运行时键盘与触屏输入被忽略，需要人工操作时先点「停止 AI 演示」。

## 9.3 记录只在“本局结束”时写入

一局从开始到结束（死局 / 主动重开 / 达成 2048 后保存）才会产生一条记录，避免同一次游玩被拆成多条；同时用 `roundEnded` 做幂等保护，防止重复写入。
